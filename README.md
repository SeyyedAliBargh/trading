# Task Force Wallex Agent

ایجنت معامله‌گر خودکار اسپات برای چالش والکس — نسخه‌ی تیم Task Force.

این پروژه یک ربات معاملات الگوریتمی است که بر پایه‌ی داده‌های بازار، مدل‌های هوش مصنوعی و قوانین ریسک طراحی شده است. هدف اصلی، اجرای معاملات اسپات در بازار Wallex به‌صورت خودکار، با تمرکز روی کارکرد درست، شفافیت، ایمنی و مدیریت ریسک است.

> این پروژه برای اهداف پژوهشی و مسابقه‌ای طراحی شده است و به‌هیچ‌وجه توصیه‌ی مالی نیست.

## خلاصه‌ی پروژه

- بازار هدف: Wallex
- نوع معامله: اسپات، فقط خرید برای ورود و فروش برای خروج
- بدون اهرم و بدون شورت
- حالت‌های اجرا: Paper و Live
- تصمیم‌گیری توسط مدل‌های LLM
- اجرای ��فارش‌ها با کنترل ریسک و قوانین سخت‌گیرانه
- ذخیره‌ی وضعیت در SQLite
- لاگ‌برداری، ممیزی و گزارش‌گیری از هر تصمیم

## ویژگی‌های کلیدی

### 1) تصمیم‌گیری مبتنی بر مدل
- چند مدل LLM به‌صورت موازی روی داده‌ی بازار تصمیم می‌گیرند
- هر مدل خروجی‌ای شبیه به `BUY / SELL / HOLD` با سطح اطمینان و حد ضرر/هدف می‌دهد
- برای ورود، حداقل دو رأی هم‌جهت لازم است
- اگر خطا، timeout یا JSON نامعتبر رخ دهد، نتیجه به‌صورت HOLD در نظر گرفته می‌شود

### 2) کنترل ریسک سخت
- هیچ ورود بدون عبور از `risk/guard.py`
- فقط نمادهای مجاز در `config.py` قابل معامله هستند
- یک پوزیشن باز در هر نماد
- محدودیت‌های تعداد پوزیشن، فاصله‌ی ورود، حد ضرر روزانه و سایر قوانین ریسک به‌صورت سخت اعمال می‌شوند
- خروج‌های stop-loss و take-profit از vetoهای ورود مستثنا هستند

### 3) اجرای واقعی و امن
- ورودی به‌صورت LIMIT BUY در بهترین ask
- خروج به‌صورت MARKET SELL
- به‌روزرسانی وضعیت‌ها از SQLite و بازار
- sync اولیه با حالت فعال (paper یا live)

### 4) Paper trading واقعی
- حساب paper با سرمایه اولیه‌ی مشخص شروع می‌کند
- پر شدن سفارش‌ها با استفاده از order book واقعی شبیه‌سازی می‌شود
- کارمزد و اسپرد همواره اعمال می‌شوند
- گزارش‌ها به‌صورت صادقانه نشان می‌دهند که paper به‌صورت خوش‌بینانه‌تر از live عمل می‌کند

### 5) لاگ‌گرفتن و ممیزی
- هر تصمیم، رأی، ورودی، نتیجه، خطا و وضعیت سفارش ثبت می‌شود
- گزارش‌های قابل‌خواندن برای بررسی عملکرد وجود دارد
- ساختار داده‌های SQLite برای ردیابی کامل پروژه مناسب است

## قوانین و محدودیت‌های مهم

- فقط نمادهای تعریف‌شده در `config.SYMBOLS` معامله می‌شوند
- هیچ کوتاه‌تری، اهرم و معامله‌ی جانبی مجاز نیست
- تصمیم مدل‌ها به‌تنهایی معامله ایجاد نمی‌کند؛ فقط guard می‌تواند veto کند
- مسیر تصمیم اگر timeout، JSON نامعتبر، خطا یا rate limit داشته باشد، نتیجه HOLD است
- خروج‌های stop-loss / take-profit هرگز نباید توسط guard یا مدل‌ها بلاک شوند
- در صورت خاموش شدن، وضعیت‌ها به‌صورت شفاف در لاگ‌ها ثبت می‌شوند
- API keyها فقط در `.env` نگهداری می‌شوند و هرگز چاپ یا ذخیره‌ی دائمی در کد انجام نمی‌شود

## مدیریت ریسک و اجرای سفارش

### ورود
- سفارش ورود با LIMIT BUY انجام می‌شود
- قیمت با توجه به best ask و تنظیمات مربوط به ticks محاسبه می‌شود
- اگر سفارش در بازه‌ی زمان تعیین‌شده پر نشد، لغو می‌شود و تصمیم HOLD در نظر گرفته می‌شود

### خروج
- خروج‌ها به‌صورت MARKET SELL انجام می‌شوند
- Stop-loss و take-profit مستقل از guard اجرایی می‌شوند
- اگر بازار به‌صورت واقعی با شکست مواجه شود، سیستم دوباره تلاش می‌کند تا در نهایت سفارش اجرا شود

### Stop-loss / Take-profit
- در حالت `SLTP_MANUAL` مقدار‌های ثابت از config استفاده می‌شوند
- در حالت غیرفعال، میانگین ارزش‌های پیشنهادی مدل‌های هم‌نظر به‌عنوان حد ضرر/هدف استفاده می‌شود
- مقادیر به‌صورت مجاز کلمپ می‌شوند و نسبت به ارزش پوزیشن محاسبه می‌شوند

## گزارش‌گیری و ممیزی

برای بررسی عملکرد و تحلیل تصمیم‌ها، سیستم لاگ‌های SQLite و اسکریپت گزارش را دارد.

```bash
python scripts/report.py
python scripts/report.py --since-hours 6
python scripts/report.py --db runtime/agent.db --run latest
```

این گزارش شامل موارد زیر است:

- وضعیت کلی پوزیشن‌ها
- تعداد تصمیم‌ها بر اساس نوع و منبع
- بازدهی/افت عملکرد
- ردهای guard و علت آن
- لاگ مدل‌ها، سفارش‌ها و رویدادها

## شفافیت و محدودیت‌ها

- عملکرد paper همواره خوش‌بینانه‌تر از واقعیت است، چون صف انتظار، latency و اختلال‌های اجرایی در آن در نظر گرفته نمی‌شود
- مدل‌های LLM تصمیم می‌گیرند اما قضاوت نهایی در حوزه‌ی ریسک به guard سپرده می‌شود
- توازن میان هزینه‌ی کارمزد، اسپرد و سود بالقوه، از مهم‌ترین ملاحظات است
- نتیجه‌ی نهایی عملکرد باید با گزارش‌های لاگ، سناریوی paper و داده‌های واقعی مقایسه شود
