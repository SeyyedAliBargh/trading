# Task Force Wallex Agent
 
ایجنت معامله‌گر خودکار اسپات برای **چالش والکس** (هکاتون Agentic AI استارکوچ) — تیم **Task Force**.
 
ایجنت به‌صورت کاملاً خودکار روی بازار اسپات والکس (فقط خرید برای ورود و فروش برای خروج، بدون اهرم و شورت) معامله می‌کند. تصمیم ورود با **رأی‌گیری سه مدل زبانی موازی** گرفته می‌شود، یک **guard ریسک** مستقل می‌تواند آن را وتو کند، و یک **نگهبان (guardian)** جدا از مدل‌ها حد ضرر و حد سود را اجرا می‌کند. هر تصمیم با دلیل مدل‌ها در SQLite ثبت می‌شود.
 
> این پروژه یک ابزار فنی برای هکاتون است، نه توصیه‌ی مالی. سرمایه‌ی کم و بازه‌ی سه‌روزه یعنی شانس نقش بزرگی در نتیجه دارد.

## ۱. مسئله و قوانین چالش
 
- مدت: ۳ روز. سرمایه‌ی اولیه: ۵ میلیون تومان. برداشت غیرفعال است.
- فقط معاملات الگوریتمی. معامله‌ی دستی، wash trade و self-trading ممنوع است.
- سود خالص برای تیم است و ضرر روی تیم نیست.
- **بازدهی = (ارزش نهایی − ۵٬۰۰۰٬۰۰۰) / ۵٬۰۰۰٬۰۰۰** در لحظه‌ی پایان رسمی، به تومان. باقی ماندن کوین باز در پایان خلاف روح قانون است، پس پوزیشن‌ها قبل از پایان بسته می‌شوند.

## ۳. استراتژی
 
### رأی‌گیری سه‌مدلی
هر چرخه برای هر ارز، سه مدل موازی یک ورودی فشرده (کندل‌های ۱۵ دقیقه، ۱ ساعت و ۴ ساعت، فیچرها، دفتر سفارش، هزینه‌ها و محدوده‌ی مجاز SL/TP) را می‌گیرند و خروجی JSON می‌دهند:
 
```json
{"action": "BUY|SELL|HOLD", "confidence": 0.0-1.0, "stop_pct": 0.015, "target_pct": 0.03, "reason": "..."}
```
 
- ورود فقط وقتی انجام می‌شود که **حداقل ۲ مدل هم‌جهت** (BUY) باشند؛ در غیر این صورت HOLD.
- خروجی نامعتبر، timeout یا خطای مدل = HOLD (رأی نامعتبر هرگز BUY حساب نمی‌شود).
- SL/TP پیشنهادی میانه‌ی مدل‌های هم‌رأی است و در بازه‌ی مجاز config کلمپ می‌شود.
- هر تلاش HTTP به مدل در جدول `llm_calls` ثبت می‌شود (توکن، تأخیر، خروجی خام کوتاه‌شده، خطا).
### چرا `net_edge`
هزینه‌ی رفت‌وبرگشت (دو بار کارمزد taker به‌علاوه‌ی اسپرد) چند دهم درصد است و روی سودهای کوچک غالب می‌شود. guard قبل از هر ورود این را حساب می‌کند:
 
```
net_edge = p * target - (1 - p) * stop - round_trip_cost
round_trip_cost = 2 * taker_fee + spread
ورود فقط اگر net_edge >= min_net_edge_pct (پیش‌فرض 0.002)
```
 
که `p` میانگین confidence مدل‌های هم‌رأی است. مدل‌ها مسئول تخمین احتمال هستند و هزینه‌ها را guard اعمال می‌کند.
 
### ورود و خروج
- **ورود:** LIMIT BUY با قیمت «عمق‌آگاه» (سقف اسلیپیج ۰٫۳٪)، صبر تا `entry_fill_timeout_sec`؛ اگر پر نشد لغو می‌شود. پس از لغو سفارش دوباره خوانده می‌شود تا پر شدن هم‌زمان با لغو از دست نرود. پرشدن جزئی نگه داشته می‌شود و SL/TP روی میانگین قیمت واقعی محاسبه می‌شود.
- **خروج:** ابتدا MARKET SELL. اگر بازاری رد شود (مثلاً ارزهایی که `is_market_type_enable=False` دارند) به LIMIT SELL قابل‌اجرا (best bid منهای چند تیک) با قیمت‌گذاری پلکانی می‌رود. تا بسته شدن کامل تلاش مجدد با backoff ادامه دارد.
- **مقدار فروش** از موجودی `free` همان دارایی خوانده می‌شود، نه از `executedQty`، چون کارمزد خرید ممکن است از خود کوین کم شود.
- **محرک رویداد (بدون LLM):** حرکت بیش از `trigger_move_pct` در `trigger_window_sec` برای ارز بدون پوزیشن، یک چرخه‌ی تصمیم خارج از نوبت راه می‌اندازد (با cooldown).
### نسخه‌ی پرامپت
پرامپت نسخه‌دار است (`PROMPT_VERSION`) و در هر run ثبت می‌شود. نسخه‌ی فعلی مدل را به تخمین احتمال بر پایه‌ی روند، مومنتوم، حجم و دفتر سفارش، متناسب با رژیم نوسان، هدایت می‌کند و محدوده‌ی SL/TP را از config می‌گیرد.

## ۴. مدیریت ریسک
 
- **guard ورود (۱۲ قانون):** مجاز بودن ارز و اکشن، نبود پوزیشن باز روی همان ارز، حداکثر تعداد پوزیشن، اندازه‌ی سفارش (کسری از ارزش کل، سقف موجودی آزاد، حداقل `min_order_tmn`)، عمق کافی دفتر سفارش، انتخاب و کلمپ SL/TP، نسبت reward/risk، `net_edge`، سقف زیان ۲۴ ساعته، فاصله‌ی بین معاملات، حداقل confidence. هر قانون با مقدار و آستانه در `risk_checks` ثبت می‌شود. خرابی یک قانون = رد شدن، نه crash.
- **guard فقط وتو می‌کند** و هیچ‌وقت معامله‌ای را شروع نمی‌کند.
- **نگهبان مستقل:** هر ۱۰ ثانیه best bid هر پوزیشن را با SL/TP می‌سنجد و مستقیماً executor را صدا می‌زند. این مسیر هیچ import از guard، مدل‌ها یا main ندارد (با تست روی سورس‌کد کنترل می‌شود)، پس سقف زیان روزانه یا خرابی LLM جلوی بستن پوزیشن را نمی‌گیرد. thread نگهبان در برابر exception جان‌سخت است و خودش ری‌استارت می‌شود.
- **ری‌استارت امن:** پوزیشن‌ها از DB خوانده می‌شوند و `sync_with_exchange` با موجودی واقعی هم‌خوان‌شان می‌کند (بسته‌شده‌ی بیرونی، سفارش یتیم با پیشوند خودمان). به دارایی‌ها و سفارش‌هایی که مال ایجنت نیستند دست زده نمی‌شود.
- **قفل per-symbol** مانع اقدام هم‌زمان دو thread روی یک ارز می‌شود.
- **خطای 429 والکس** روی مسیر تصمیم یعنی HOLD و backoff (شروع ۲ ثانیه، سقف ۶۰ ثانیه).
- **خاموشی:** `CLOSE_POSITIONS_ON_SHUTDOWN` پیش‌فرض `False` است و فقط هشدار بلند می‌دهد. قبل از آخرین خاموشی باید `True` شود تا همه‌ی پوزیشن‌ها بسته شوند.

## ۵. لاگ تصمیم و گزارش‌ها
 
برای **هر معامله** زنجیره‌ی کامل در SQLite (`runtime/agent.db`) هست: ردیف تصمیم، رأی و دلیل هر مدل (`llm_calls`)، نتیجه‌ی هر قانون guard (`risk_checks`)، سفارش‌ها، تلاش‌های بستن و PnL واقعی. هر چرخه یک `decision_uid` دارد که در تصمیم و رویدادهای مرتبط ثبت می‌شود.
 
گزارش ممیزی (فقط‌خواندنی، حتی هم‌زمان با اجرای ربات):
 
```bash
python scripts/report.py                # آخرین run
python scripts/report.py --since-hours 6
python scripts/report.py --db runtime/agent.db --run latest
```
 
شامل: معادل equity و افت سرمایه، تعداد تصمیم‌ها به تفکیک اکشن و منبع، تفکیک ردهای guard (با تأکید بر `net_edge`)، لاگ هر معامله با دلیل مدل‌ها، آمار LLM (نرخ خطا، میانگین و p95 تأخیر، توکن) و خلاصه‌ی رویدادها.
 
### داشبورد
یک داشبورد فقط‌خواندنی که با همان `main.py` بالا می‌آید (آدرس پیش‌فرض `http://127.0.0.1:8765`) و رأی و دلیل هر مدل، نتیجه‌ی guard، پوزیشن‌های باز و معاملات را نشان می‌دهد؛ با `--no-ui` خاموش می‌شود.

## ۶. اجرای مجدد
 
پیش‌نیاز: ویندوز یا لینوکس، Python 3.14 (نسخه‌ی تست‌شده)، کلید API والکس و کلید BoxAPI.
 
```bash
git clone <repo-url>
cd trading_agent
python -m venv venv
venv\Scripts\activate            # لینوکس: source venv/bin/activate
pip install -r requirements.txt
copy .env.example .env           # لینوکس: cp .env.example .env
```
 
`.env` را با کلیدها پر کنید (نام دقیق متغیرها در `.env.example` است). **این فایل هرگز commit نمی‌شود.**
 
### حالت‌ها
متغیر `DRY_RUN` در `.env` تنها کلید تغییر حالت است:
 
| `DRY_RUN` | رفتار |
|---|---|
| `true` | **Paper:** سفارش‌ها روی دفتر سفارش واقعی با کارمزد و اسپرد شبیه‌سازی می‌شوند؛ هیچ درخواست نوشتنی به والکس نمی‌رود (با تست تأیید شده). |
| `false` | **Live:** سفارش واقعی. بنر قرمز «LIVE-MONEY» در شروع چاپ می‌شود. |
 
### دستورها
 
```bash
python main.py --once        # یک چرخه روی همه‌ی ارزها و خروج
python main.py               # اجرای مداوم (ربات + نگهبان)
python scripts/report.py     # گزارش ممیزی
python scripts/reset_paper.py  # ریست حساب paper
pytest -q                    # تست‌ها (بدون شبکه)
```
 
ارزها فقط در `config.py` (`CONFIG.SYMBOLS`) تعریف شده‌اند و هیچ ماژولی ارز را هاردکد نمی‌کند.
 
### اجرای ۳ روزه
ربات باید روی سیستمی پایدار (ترجیحاً سرور) با ری‌استارت خودکار اجرا شود، نه لپ‌تاپ؛ اگر پروسه بمیرد پوزیشن باز بدون نگهبان می‌ماند.

## ۷. شفافیت و محدودیت‌ها
 
- **سود paper خوش‌بینانه است:** پر شدن سفارش‌ها روی دفتر بدون صف و بدون اثر بازار فرض می‌شود.
- **نمونه‌ی ۳ روزه با سرمایه‌ی کم:** شانس سهم بزرگی دارد؛ هدف واقع‌بینانه بازدهی مثبت، افت کم و لاگ شفاف است، نه وعده‌ی سود.
- **هزینه‌ی رفت‌وبرگشت (~۰٫۶ تا ۰٫۹٪)** مانع بزرگی است؛ برای همین `net_edge` سخت‌گیرانه است و ممکن است تعداد معاملات کم باشد.
- مسیرهای اجرای واقعی (پر شدن واقعی، MARKET SELL بدون قیمت، رفتار دقیق status های `FILLED`/`PARTIALLY_FILLED`، پنجره‌ی rate limit) فقط با fake و paper تست خودکار شده‌اند؛ status ها و چرخه‌ی ثبت و لغو سفارش با probe واقعی تأیید شده‌اند. executor به `active` و `executedQty` تکیه می‌کند، نه به رشته‌ی status.
- بک‌تست کامل انجام نشده؛ کیفیت تصمیم LLM با shadow و لاگ‌ها سنجیده می‌شود.
- خبر، Fear & Greed و trailing stop پیاده‌سازی نشده‌اند.
- حداقل سفارش اسپات زیر ۸۵ هزار تومان مشاهده شد؛ ایجنت خودش حداقل ۱۰۰ هزار تومان را اعمال می‌کند.
